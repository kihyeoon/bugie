# 에러 수집 기본 원리

## 왜 에러 수집이 필요한가?

앱이 사용자 손에 들어가면 개발자의 콘솔은 보이지 않는다. 사용자가 "앱이 꺼졌어요"라고 말해도 **어디서, 왜, 어떤 상황에서** 문제가 발생했는지 알 수 없다.

에러 수집은 이 간극을 메운다:
- 크래시가 발생하면 **자동으로 개발팀에게 보고**
- **스택 트레이스**(에러가 발생한 코드 경로)를 수집해서 원인 파악
- 얼마나 많은 사용자에게 영향을 미치는지 **규모 파악**
- 사용자가 리포트하기 전에 **선제적 대응** 가능

---

## 동작 원리

### 1단계: 에러 캡처 (클라이언트)

앱에 SDK(Sentry)를 설치하면 자바스크립트 런타임의 에러 핸들러를 **가로챈다(intercept)**:

```
[앱 코드에서 에러 발생]
        ↓
[JS 런타임의 global error handler]
        ↓
[Sentry SDK가 가로챔]  ← 여기서 에러 정보를 수집
        ↓
[에러 정보를 패키징]
```

수집하는 정보:
- **스택 트레이스** — 에러가 발생한 함수 호출 경로 (`add.tsx:45 → TransactionService:120 → SupabaseRepository:88`)
- **브레드크럼** — 에러 직전의 사용자 행동 기록 (어떤 화면을 보고 있었는지, 어떤 버튼을 눌렀는지)
- **컨텍스트** — 기기 정보(iPhone 15, iOS 18), 앱 버전, OS 버전
- **태그** — 개발자가 직접 추가한 메타데이터 (현재 가계부 ID 등)

### 2단계: 전송 (클라이언트 → 서버)

```
[Sentry SDK]
    ↓ HTTPS POST (JSON payload)
[Sentry 서버 (클라우드)]
    ↓
[이벤트 처리 파이프라인]
    ↓
[대시보드에 표시]
```

- 에러 정보는 JSON으로 직렬화되어 Sentry 서버로 전송
- 네트워크가 없으면 로컬에 캐싱 → 연결 복구 시 전송
- **소스맵(Source Map)** 을 활용해 번들된 코드를 원본 코드 위치로 매핑

### 3단계: 집계·분석 (서버)

```
[동일한 에러를 그룹핑]  ← "fingerprinting" — 같은 원인의 에러를 하나의 이슈로 묶음
        ↓
[영향 범위 계산]       ← 몇 명의 사용자에게 영향?
        ↓
[알림 발송]           ← Slack/이메일로 개발팀에게 통보
        ↓
[대시보드 시각화]      ← 트렌드, 빈도, 기기별 분포
```

---

## 에러의 3가지 유형

| 유형 | 설명 | 수집 방식 |
|------|------|----------|
| **네이티브 크래시** | 앱이 완전히 종료됨 (C++/ObjC 레벨) | Sentry가 시그널 핸들러로 자동 캡처, 다음 실행 시 전송 |
| **JS 예외** | `throw new Error()`, 미처리 Promise reject | 글로벌 에러 핸들러로 자동 캡처 |
| **수동 캡처** | 개발자가 의도적으로 보고 (API 실패 등) | `Sentry.captureException(error)` 호출 |

## 핵심 개념

### Sentry.wrap()이 하는 일

```typescript
export default Sentry.wrap(function RootLayout() { ... });
```

이 한 줄이 하는 일:
1. React 컴포넌트 트리 전체를 **ErrorBoundary**로 감쌈 → 렌더링 에러 캡처
2. **글로벌 에러 핸들러** 등록 → 미처리 예외/Promise reject 캡처
3. **네이티브 크래시 핸들러** 등록 → 앱 강제 종료 시 캡처
4. **성능 모니터링** 시작 → 화면 로드 시간 자동 측정

### 소스맵이 중요한 이유

프로덕션 앱의 JS 코드는 번들링·난독화된다:

```
// 실제 에러 로그 (소스맵 없이)
Error at e.run (bundle.js:1:234567)

// 소스맵 적용 후
Error at TransactionService.save (TransactionService.ts:120:15)
```

EAS Build 시 Sentry가 자동으로 소스맵을 업로드하면, 대시보드에서 **원본 파일명:줄번호**로 표시되어 디버깅이 가능해진다.

### 브레드크럼 = 에러의 타임라인

에러가 발생하기 직전 사용자가 뭘 했는지 시간순으로 기록한다:

```
10:30:01  [navigation] 홈 → 추가 탭
10:30:05  [ui.click]   카테고리 "식비" 선택
10:30:08  [ui.input]   금액 입력: 12000
10:30:10  [ui.click]   "저장하기" 버튼 탭
10:30:10  [http]       POST /rest/v1/transactions → 500 Internal Server Error
10:30:10  [error]      TransactionService.save: relation "transactions" does not exist
```

이렇게 되면 "거래 저장 시 서버 에러가 발생했고, 그 전에 식비 카테고리로 12000원을 입력한 상황"이라는 맥락을 알 수 있다.

### ErrorBoundary

React의 에러 경계 컴포넌트. 자식 컴포넌트 트리에서 렌더링 에러가 발생하면:
1. 에러를 Sentry에 보고
2. 앱 전체가 크래시되는 대신 **대체 UI(fallback)** 표시
3. "다시 시도" 버튼으로 복구 가능

```
[정상 상태]                    [에러 발생 시]
┌──────────────────┐          ┌──────────────────┐
│    홈 화면        │          │                  │
│  ┌────────────┐  │          │  문제가 발생했습니다 │
│  │ 캘린더      │  │    →     │                  │
│  │ 월간 요약   │  │          │  [다시 시도]      │
│  └────────────┘  │          │                  │
└──────────────────┘          └──────────────────┘
```

### Fingerprinting

동일한 원인의 에러를 하나의 "이슈"로 그룹핑하는 방식:

```
에러 A: TransactionService.save() at line 120 → NullPointerError  ─┐
에러 B: TransactionService.save() at line 120 → NullPointerError  ─┼→ Issue #1234
에러 C: TransactionService.save() at line 120 → NullPointerError  ─┘     (발생 3회)

에러 D: AuthService.login() at line 45 → NetworkError             ─→ Issue #1235
                                                                        (발생 1회)
```

100개의 에러가 발생해도, 원인이 2가지라면 이슈는 2개만 생긴다. 이를 통해 "가장 많이 발생하는 이슈"를 우선 수정할 수 있다.

---

## 한줄 요약

**에러 수집 = 사용자 기기에서 발생한 문제를 자동으로 감지 → 맥락과 함께 서버로 전송 → 그룹핑·분석·알림**하는 시스템. 개발자가 직접 재현하지 않아도 원인을 파악할 수 있게 해준다.
